## 5. 升级与版本管理策略（"以后升级怎么做合适"）

### 5.1 版本号规范（语义化）
- 格式：`主.次.修订`，当前 `1.0`。
  - **主版本**：产品大方向/底层架构变更（如从原型转正式上线 → v5）。
  - **次版本**：新增一个完整功能模块（如新增"催收闭环" → 1.0）。
  - **修订版本**：模块内优化/修复（如订单列表展示商品明细 → 1.0）。
- 原型、PRD、TDD、ERD、API、用户手册、部署运维 **共用同一版本号**，避免文档与实现脱节。

### 5.2 迭代节奏（推荐工作流）
```
需求确认 → 原型改动(单 HTML) → JS 语法校验 → 文档六件套同步 → 内部评审
   → 客户确认 → (若需)后端落地 → 回归测试 → 版本发布 + 变更记录
```
- **原型先行**：需求未定时用单 HTML 原型快速验证交互，低成本试错。
- **文档即门禁**：每次改原型必须同步对应文档（本项目已固化为习惯），否则视为未完成。
- **范围门**：MVP 11 项为**最终功能范围**，开发期内不接受范围膨胀；范围外需求一律走"独立升级模块"通道（机制见《小程序 MVP 落地计划与技术架构》§7 升级机制）。

### 5.3 变更记录规范
- 每个版本在 PRD / 用户手册文末维护"变更记录"表（版本 / 日期 / 变更点 / 影响文档）。
- 重大架构变更在 TDD/ERD 顶部用 `> 注意：vX.Y 起……` 标注历史字段去留。

### 5.4 灰度与回滚
- 原型：用 git 分支/标签管理，每个发布版本打 tag（如 `proto-1.0`）。
- 正式上线：云开发环境分 **预览环境 / 生产环境**，新功能先发预览，老板/管理员验收后再切生产。
- 数据：升级前备份云数据库集合，支持回滚。

### 5.5 文档与代码一致性自检清单（每次发布前）
- [ ] 原型版本号 = 各文档版本号
- [ ] 新增/删除字段已在 ERD + API + TDD 同步
- [ ] 角色权限矩阵在 README + PRD + 用户手册 三处一致
- [ ] 状态机在 README + PRD + 业务流程全景 三处一致
- [ ] MVP 不含项已明确标注为"独立升级模块"，未误入交付
- [ ] MVP 11 项范围与《小程序 MVP 落地计划与技术架构》§一 完全一致
