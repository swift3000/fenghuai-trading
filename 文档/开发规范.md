# 丰淮商贸采购下单助手 — 开发规范（总纲）

> **文档版本**：v1.0
> **编写日期**：2026-07-29
> **适用对象**：产品经理（技术小白）主导开发 + AI 协作
> **核心理念**：规范不是束缚，而是「让小白也能做出专业产品」的脚手架

---

## 0. 写在前面：为什么要规范？

### 一个类比：开餐厅

| 角色 | 类比 | 在项目里 |
|------|------|----------|
| 菜谱 | PRD/设计文档 | 决定做什么菜 |
| 厨房动线 | 目录结构/规范 | 决定怎么做菜不乱 |
| 刀工火候 | 代码规范 | 决定菜好不好吃、稳不稳 |
| 出餐检查 | 测试规范 | 决定菜能不能上桌 |
| 复盘改进 | 运维规范 | 决定下次能不能做得更好 |

**没有规范的厨房**：盐放哪不知道、刀乱放、菜上桌忘了验——一定会乱。
**有规范的厨房**：每个东西有固定位置，新人来了照着做也不会出错。

**对技术小白的意义**：你不是要成为大厨，而是要让厨房按规矩运转，AI（你的副厨）按你的指挥做菜，你看得懂、改得对、控得住。

### 三条铁律（贴在墙上）

1. **先想后做**：任何功能，先在文档/原型里讲清楚，再写代码。
2. **小步快跑**：一次只做一个功能，做完验证，再做下一个。不要一次堆 10 个功能。
3. **能跑才算数**：代码能运行、能测试、能验收，才算完成。"差不多写完了"=没完成。

## 1. 生命周期总览：7 个阶段

本项目从 0 到 1，按以下 7 个阶段推进。每个阶段都有「输入、产出、验收标准」。

```
需求 → 设计 → 搭建 → 开发 → 测试 → 部署 → 运维
 ↓     ↓     ↓     ↓     ↓     ↓     ↓
PRD   TDD   脚手架  功能   用例   上线   监控
```

| 阶段 | 做什么 | 谁主导 | 产出物 | 验收标准 |
|------|--------|--------|--------|----------|
| 1. 需求 | 写清要做什么 | PM（你） | PRD、原型 | 业务方确认签字 |
| 2. 设计 | 写清怎么做 | PM+AI | TDD、ERD、API文档 | 技术方案可落地 |
| 3. 搭建 | 建厨房 | AI+PM | 项目脚手架、目录、配置 | 项目能空跑起来 |
| 4. 开发 | 写功能代码 | AI写+PM审+PM改 | 模块代码 | 单功能可演示 |
| 5. 测试 | 验菜 | PM | 测试用例、缺陷清单 | 核心流程跑通 |
| 6. 部署 | 上桌 | AI+PM | 线上环境、版本号 | 真机能用 |
| 7. 运维 | 复盘改进 | PM+AI | 监控、日志、迭代计划 | 问题可追溯 |

> **现状**：本项目已完成阶段 1、2（PRD/TDD/ERD/API 均已定稿），下一步是阶段 3「搭建」。

## 2. 阶段一：需求阶段规范

### 2.1 原则：需求不清晰，不动代码

任何新功能开始前，必须能用一句话回答三个问题：
1. **给谁用？**（角色）
2. **解决什么问题？**（价值）
3. **怎么算成功？**（验收标准）

### 2.2 PRD 编写规范

- 一个功能一个模块，模块内分「目标-流程-规则-异常」四段
- 所有交互必须有原型对应（本项目已用 HTML 原型）
- 边界情况必须写明：空数据、超长输入、断网、并发等
- 每条需求编号（如 `REQ-订单-001`），便于追溯

### 2.3 需求变更规范

- 变更必须记录在 `文档/变更记录.md`（待建）
- 变更影响评估：是否影响已有功能、工期、数据结构
- 变更超过 3 处需重新评审，避免「需求蔓延」

## 3. 阶段二：设计阶段规范

### 3.1 三份必备文档

| 文档 | 作用 | 状态 |
|------|------|------|
| TDD 技术规格书 | 架构、模块、技术选型 | ✅ 已有 |
| ERD 数据库设计 | 集合、字段、索引 | ✅ 已有 |
| API 接口文档 | 云函数入参/出参/错误码 | ✅ 已有 |

### 3.2 设计原则

- **简单优先**：能 1 张表解决的，不用 3 张表；能 1 个云函数解决的，不拆 3 个
- **快照优于关联**：订单存商品快照，不依赖商品表实时查（商品改价不影响历史订单）
- **预留扩展不预实现**：字段可预留注释，但不写未使用的代码

## 5. 阶段四：开发阶段规范

> 详见配套文档 [代码规范.md](./代码规范.md)。这里只讲流程。

### 5.1 开发流程（一个功能的完整生命周期）

```
1. 读 PRD → 2. 看原型 → 3. 定接口 → 4. 写云函数 → 
5. 写前端 → 6. 联调 → 7. 自测 → 8. 提交 → 9. 验收
```

**每一步的检查点**：
- 第 3 步：接口入参出参写进 API 文档再开发
- 第 7 步：必须用真实数据跑一遍，不能只看「不报错」
- 第 8 步：提交信息按 Git 规范（见 [Git协作规范.md](./Git协作规范.md)）

### 5.2 任务拆分原则

- 一个任务不超过半天工作量（小白节奏，宁可拆细）
- 任务粒度：「新增一个商品」「修复订单列表分页」，不要「做完订单模块」
- 用 TodoWrite 记录任务，做完一个划掉一个

### 5.3 AI 协作规范（你与 AI 的分工）

| 你负责 | AI 负责 |
|--------|---------|
| 讲清需求、验收结果 | 写代码、解释代码 |
| 决定要不要改 | 提供方案、给出建议 |
| 改文案、调样式、提交 Git | 重构、调试、生成测试 |
| 把控业务正确性 | 把控技术正确性 |

**黄金法则**：AI 写的代码，你要看得懂、改得动。看不懂就让它解释，解释完还不懂就让它简化。

## 6. 阶段五：测试规范

### 6.1 测试分层（小白版）

| 层级 | 做什么 | 谁做 |
|------|--------|------|
| 自测 | 写完功能自己点一遍 | 你+AI |
| 流程测试 | 完整业务流程跑通（下单→审核→打印） | 你 |
| 异常测试 | 断网、空数据、超长输入、重复提交 | 你 |
| 上线前回归 | 新功能不影响老功能 | 你 |

### 6.2 测试用例模板

每个核心功能维护一份用例表：

| 用例ID | 场景 | 操作步骤 | 预期结果 | 实际结果 | 通过 |
|--------|------|----------|----------|----------|------|
| TC-订单-001 | 正常下单 | 选客户→选商品→提交 | 生成订单，状态待审核 | | ☐ |

### 6.3 缺陷管理

- 发现 bug 立即记录在 `文档/缺陷记录.md`（待建）
- 字段：编号、发现时间、场景、复现步骤、严重程度、状态
- 严重程度：🔴 阻断 / 🟠 严重 / 🟡 一般 / 🟢 轻微

## 7. 阶段六：部署规范

### 7.1 版本号规范（语义化版本）

```
v主版本.次版本.修订号   例如 v0.1.0
```

- 主版本：架构大改（v0→v1）
- 次版本：新增功能
- 修订号：修复 bug

### 7.2 发布流程

1. 测试环境通过 → 2. 打版本 tag → 3. 部署生产 → 4. 冒烟测试 → 5. 公告
- **每次发布必须有回滚方案**（保留上一版本云函数代码）

### 7.3 发布清单

- [ ] 测试环境已通过核心流程
- [ ] 数据库已备份（云开发控制台一键备份）
- [ ] 云函数已上传部署
- [ ] 小程序已提审（小程序端）
- [ ] Web 后台已发布静态托管
- [ ] 线上冒烟测试通过

## 8. 阶段七：运维规范

### 8.1 监控（用云开发自带能力）

- 云函数日志：定期查看错误日志
- 数据库监控：关注慢查询、集合大小
- 告警：云开发控制台配置错误告警

### 8.2 数据安全

- **数据库定期备份**（每周一次手动备份，重大变更前必备份）
- 敏感操作（删除商品/客户/订单）必须二次确认 + 软删除
- 管理员密码定期更换，离职账号立即禁用

### 8.3 迭代节奏

- 每周一次小复盘：本周做了什么、遇到什么问题、下周计划
- 每个版本一次大复盘：用户反馈、数据指标、下版本优先级

## 10. 如何使用本规范

1. **新功能开始前**：读第 2、3 节，确认需求和设计清楚
2. **写代码时**：遵循《代码规范.md》
3. **每次提交时**：按《Git协作规范.md》写提交信息，对照《开发检查清单.md》自查
4. **测试时**：按第 6 节执行
5. **发布时**：按第 7 节走流程
6. **遇到问题**：回到对应阶段找规范，不要跳过

**记住**：规范是帮你的，不是限制你的。觉得哪里不合理，记下来，复盘时调整。但调整前，先按规范走一遍。
